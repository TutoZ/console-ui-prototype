# 完整交互 Spec｜培训后经验证再上岗

功能 ID：JXL-TRAIN-01 · 版本 0.1 · 2026-09-08。

成熟度：可开始原型试点的建议规格；业务规则需在试点启动时采纳/修订，服务端接口待研发确认。不是当前实现说明，不表示用例已经通过。

## 1. 需求输入卡

| 项目 | 定义 |
|---|---|
| 用户 | 负责在线客服数字员工培训与上岗的业务管理者 |
| 场景 | 员工已用 V1 接待；管理者修改培训要求，希望测试 V2 后再决定是否应用 |
| 用户意图 | “先教会它新的要求，确认表现合格，再让它按新要求接待。” |
| 当前问题 | 保存回调更新 publishedSnapshotId；应用历史存档直接更新配置；普通客服完成培训处理未见测试通过记录校验。是静态代码发现，不是实际事故或用户访谈结论 |
| 期望结果 | 保存、测试、应用含义清晰；V1 继续服务，V2 在验证并确认后只用于新会话；结果和版本能追溯 |
| 主要主张 | E2 完全掌控、E5 养成归属、E6 专业胜任 |
| 基线主张 | E1 下一步可理解；E3 测试证据真实；E4 保留培训/上岗心智 |
| 本期范围 | 在线客服单员工：修改 → 保存 → 测试 → 确认应用；覆盖失败、版本过期、回退、权限、并发 |
| 本期不做 | 所有业务域统一改造、自动持续学习、批量发布、流量灰度、训练模型本身 |
| 交付 | 一组连贯页面状态、可运行原型、16 条用例、联调依赖与证据报告 |

首次上岗：没有当前上岗存档，走相同的保存/测试/确认流程，确认文案用“准予上岗”；已上岗员工用“应用到新会话”。“完成培训”只退出工作区，不代表应用成功。

## 2. 与主框架的关系

入口：“我的数字员工”或“在线客服 → 员工培训”中的同一员工。复用 EmployeeManagePage 与现有入职培训工作区、能力测试、培训存档组件，不新建一级导航。

工作区固定显示员工姓名、岗位、在岗状态和当前上岗存档。左侧编辑培训要求，右侧在“能力测试 / 培训存档”中切换。修改中的内容不能覆盖当前上岗存档展示。

本功能覆盖 F01–F08；质检有独立入口，不纳入本次试点。入口返回后保留原业务域、员工列表搜索条件；带未保存更改离开时询问保存或放弃，关闭询问则留在原处。

## 4. 角色与权限（建议能力名，需映射现有角色体系）

| 权限能力 | 查看 | 编辑与保存 | 测试 | 应用/上岗 |
|---|---|---|---|---|
| 只读观察者 | 授权员工及记录 | 否 | 否 | 否 |
| 培训者 | 是 | 是 | 是 | 否 |
| 上岗管理者 | 是 | 依已有编辑权限 | 依已有测试权限 | 是 |

“上岗管理者”是能力描述，不要求新增角色名称。不能因为拥有查看权限就获得应用权限。团队、员工、知识、技能和渠道授权均在服务端检查；当前原型可模拟权限，但报告必须标出。

## 5. 数据与有效性

| 字段/对象 | 用途与校验 |
|---|---|
| employeeId / teamId | 稳定关联，必填，服务端验证归属 |
| draftRevision | 草稿修订号；保存/编辑提交时检测冲突 |
| candidateSnapshotId | 本次目标存档 ID；显示用 V2 等易读编号，ID 不随标题变化 |
| activeSnapshotId | 当前上岗存档，与候选分离；现有 publishedSnapshotId 需评估迁移，不能直接假定已分离 |
| configurationFingerprint | 配置、知识/技能版本、模型版本、渠道能力依赖的组合标识 |
| testRunId / testSuiteVersion / rubricVersion | 保存测试来源与评价规则；通过只对当前组合有效 |
| testEvidence | 每个用例输入、预期检查点、实际输出、依据、结论、来源；缺失项不能算通过 |
| applicationRequestId / expectedActiveSnapshotId | 防重复与并发校验；超时继续查询同一请求 |
| sessionSnapshotId | 会话开始时绑定版本；是 R07 的必要后端能力 |

知识/技能/模型或评价规则变化导致证据失效时提示重新测试。首期不另加“过 7 天自动失效”之类任意时效；若业务需要有效期，产品经理单独定义。旧记录仍保留，但不再授权新应用。未保存新草稿不修改旧存档内容，旧存档测试在其原有条件下仍可查看。

## 6. 状态转换与失败恢复

状态分四组，允许并存，例如“员工在岗 + 草稿未保存 + 候选测试中”。

| 状态组 | 状态 |
|---|---|
| 员工运行 | 未上岗 / 在岗 / 休息；由既有生命周期管理 |
| 编辑 | 无更改 / 未保存 / 保存中 / 保存失败 / 只读预览 |
| 候选测试 | 未测试 / 测试中 / 通过 / 未通过 / 运行异常或部分完成 / 证据失效 |
| 应用 | 未提交 / 待确认 / 提交中 / 结果未知 / 成功 / 失败 / 并发冲突 |

| 触发 | 前置条件 | 转换与界面反馈 | 失败或退出 |
|---|---|---|---|
| 修改培训要求 | 编辑权限、非预览 | 标记未保存；当前上岗版本不变 | 输入校验就地指出，不清空 |
| 保存培训 | 字段有效且有修改 | 保存中禁重复；成功生成 V2，提示“已保存，尚未应用” | 失败保留草稿；结果未知用请求标识查回，避免重复存档 |
| 启动能力测试 | 已保存 V2、无脏草稿、依赖可用 | 测试中显示目标版本和真实完成数；结果进入通过/未通过/部分完成 | 保留已完成项及失败原因，可修正或重试；取消等待执行端确认 |
| 测试后继续修改 | 可编辑 | 新草稿未保存；应用入口解释为何不可用 | 原 V2 测试记录仍可看，新内容不可借用 |
| 点击应用 | R05 满足 | 展示变更与影响确认弹窗 | 取消不改任何运行状态 |
| 确认应用 | 再次校验条件与 expectedActiveSnapshotId | 提交中；成功后更新当前上岗标识及事件记录 | 明确失败保留原版；结果未知先查询，不能假定失败或成功 |
| 查看历史存档 | 查看权限 | 只读预览标识，编辑/测试/应用入口锁定，提示退出预览后操作 | 关闭预览返回原草稿，不覆盖编辑 |
| 请求回退 | 退出预览，选择历史目标 | 重新计算资格，通过则走应用确认 | 测试证据失效则先复测 |
| 切换员工或离开 | 无更改直接离开 | 有更改显示保存后离开/放弃/继续编辑 | 保存失败留在当前页；运行中的服务任务不因离开而取消 |

建议原型默认：操作即时呈现忙碌反馈；应用超过 10 秒未获终态显示“正在确认结果”，每 3 秒查询一次，60 秒后停止自动查询并保留手动查询入口。数值不是现网 SLA，联调前由研发与产品确认；停止查询不代表任务取消。

## 7. 页面规格与文案

| 区域 | 内容和动作 | 关键约束 |
|---|---|---|
| 固定页头 | 员工/岗位/在岗状态/当前上岗存档；返回与完成培训 | 版本和在岗状态分开；不因草稿变化而跳动 |
| 培训编辑区 | 原有岗位、约束、知识技能字段；差异摘要；保存培训 | AI 建议先进入草稿，关键要求不自动覆盖；沿用原有字段校验 |
| 能力测试区 | 目标版本、固定测试集、运行状态、各项检查结果、证据 | 显示“演示数据”或真实环境；部分完成不显示总通过 |
| 培训存档区 | 版本、保存时间、变化摘要、测试资格、当前上岗标识；查看/选择应用/删除 | 历史非当前不等于失效，失效需具体原因；不可借“接待中”表示存档资格 |
| 应用确认弹窗 | V1 → V2、改了什么、影响渠道、新会话生效、原会话继续 V1 | 主按钮“确认应用”；取消/关闭均无副作用 |
| 应用结果区 | 当前版本、成功时间、请求记录；失败恢复或查询 | Toast 只作辅助，持久状态可回看 |

关键文案：

- 保存成功：“已保存为 V2，当前仍使用 V1 接待。完成能力测试后可申请应用。”
- 首次保存：“已保存为 V1，尚未上岗。请先完成能力测试。”
- 修改后：“当前有未保存更改，请先保存为新存档再测试。”
- 测试未通过：“3 项中有 1 项未通过：超出岗位范围时未转交。查看详情并修正后重测。”
- 运行异常：“测试未完成：知识检索服务暂不可用。已保留完成项，可重试。”
- 结果未知：“应用请求已提交，正在确认结果。确认前请勿重复应用。”
- 冲突：“当前上岗存档已被更新。你的草稿已保留，请查看最新版本后重新确认。”
- 应用成功：“V2 已应用到新会话，已有会话继续使用原存档。”
- 无权限：“你可以查看测试结果；应用到新会话需要上岗管理权限。”

可访问与适配：复用弹窗外壳，但现有 PanelModal 的焦点能力须补测（见 components.md 的 GAP-DIALOG-01）；目标要求为打开后焦点进入标题/首个可操作元素，Tab 不逸出，关闭后回到触发按钮；错误信息与对应字段关联。流式结果不抢焦点。1366×768 和 1024×768 验证核心操作可达；窄宽下编辑区与测试区可分段切换，保留输入与选中版本。只读和失效状态同时有文字，不只变颜色。

## 8. 固定演示数据与业务测试集

原型预置：团队“示例服务团队”；员工“售后服务专员”（明确数字员工）；在岗 V1；未保存草稿为 V2 待存档；知识 K1、技能 S1、模型 M1、测试集 Q1、评价规则 B1。所有均是模拟数据，不含真实客户资料。

业务样例仅用于演示资格机制，不规定京小灵真实售后政策：

| 样例 | 模拟输入与上下文 | 必须检查 | 失败示例 |
|---|---|---|---|
| Q1-1 资料内问题 | “服务时间是什么？”；K1 明确为工作日 9:00–18:00 | 正确回答并给 K1 依据 | 编造全天候服务 |
| Q1-2 缺必要信息 | “查一下订单进度”；无订单标识 | 请求必要标识，不猜订单状态 | 声称已发货 |
| Q1-3 超出权限 | “直接帮我改退款金额”；岗位无该权限 | 说明边界并给人工转交入口 | 宣称修改成功 |

演示资格：三个检查点全部满足，且有逐项证据，才展示模拟通过。真实测试允许措辞变化，按语义检查；模型自评只能辅助，产品经理/业务专家确定评分规则并抽查。真实上线须扩充业务样本和误判反例，本组不能证明整个岗位已胜任。

每个演示场景从相同基线重置，提供 V2 全通过、V2 有一项失败、测试服务失败、应用超时后成功、并发 V3、只读角色、依赖升级 K2 七种预置。重置仅影响演示数据，不清除真实团队数据。

## 9. 验收与接口交付

完整 16 条可执行用例见 acceptance-cases.json；使用 06-evaluation.md 的证据记录模板。任何结果初始为未执行。

需要研发提供的能力契约（未宣称有这些接口）：

| 能力 | 请求意图 | 必需结果与失败 |
|---|---|---|
| 保存候选存档 | employeeId、草稿内容、修订号、请求 ID | 返回不可变存档及依赖版本；校验/无权限/冲突/未知结果可查询 |
| 运行与查询测试 | snapshotId、测试集及规则版本 | testRunId、逐项结果、完成数量、终态和证据；支持部分完成及重试 |
| 资格检查 | 目标存档、当前依赖与权限 | 可应用布尔值及逐项阻断原因；不能只靠前端计算 |
| 应用与查询 | 目标版本、预期当前版本、请求 ID | 原子校验并应用，记录操作者/范围；幂等返回；冲突不覆盖 |
| 会话版本绑定 | 新会话读取生效版本，旧会话保留原绑定 | 可回查每个会话的实际配置和资源版本 |

真实应用资格必须在提交时再次服务端校验，以覆盖确认弹窗打开后权限/依赖变化。迁移历史存档时不能把“有存档”全部当“测试通过”；现有线上版本可继续服务，新增变更走新资格规则，迁移策略由研发和产品确认。

## 10. 实施拆分与完成定义

UI/状态原型由校招生可独立承担；资格接口、运行隔离、权限和并发由研发承担。各任务与依赖见 07-rollout.md。原型验收通过只说明交互规则可复现；真实发布必须通过联调门槛，不允许用模拟标识消失来冒充联调完成。

## 11. 0.2 单元化映射补充

按 product.md 冻结产品主线，只加载 domain.md 的 online_service 规则。保存→TPL-SAVE；测试→TPL-TEST；应用→TPL-APPLY；只读存档→TPL-HISTORY。每个模板具体元素、组件与Token绑定见 catalog.json，候选保存实例见 examples/save-plan.json。
