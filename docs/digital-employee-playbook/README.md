# 京小灵数字员工体验落地范式｜产品经理工作台

版本：0.2 · 2026-09-08 · 状态：可试用工作包，待团队试点校准。

**目标：让产品经理把业务意图写成可验证的交互要求，让校招生借助 AI，在京小灵主框架内产出符合六项体验主张的功能。**

本包交付了方法、规则、模板、完整功能 Spec、验收用例和实施任务；未宣称产品功能已完成改造，也未将模拟交互当成真实业务验证。新增规则均为本次建议，不能覆盖当前已批准的业务规则；冲突按问题单处理。

## 先用起来

1. 产品经理先按 [product.md](product.md) 填意图冻结卡：一个业务域、对象、动作和可验证结果。
2. 读取 [domain.md](domain.md) 的共性边界及匹配业务域，形成 [单功能 Spec](03-spec-template.md)。规则未知时登记，不加载其他业务来猜答案。
3. 按 [templates.md](templates.md) 选择小模板，按 [components.md](components.md) 和 [design.md](design.md) 完成槽位→组件→Token绑定；示例见 [候选保存计划](examples/save-plan.json)。
4. 用 [craft.md](craft.md) 与 [22 条原子用例](atomic-tests.md) 逐单元实现和取证，再执行原有组合用例。
5. 运行 [Design Evaluator](design-evaluator.md) 的静态检查，再做实际交互、画面和业务验证；失败回流到所属知识层。

## 三层范式，三类产出

| 参考范式 | 在京小灵里的作用 | 具体资产 |
|---|---|---|
| 设计工程 | 将六项主张、业务边界、框架与验收规则带入生成过程 | 主张、框架、Spec、组件引用、执行流程 |
| 动态交互 | 按用户意图和任务状态呈现必要信息与操作 | 意图路由、模板槽位、状态表、人工决策点、失败恢复 |
| 自我进化 | 用证据找出问题，修正规则后在另一功能中复验 | 验收报告、反例、规则变更记录、回归用例 |

这里的动态交互，可以先用确定的状态与共享组件实现，不要求首期上线由模型自由生成界面。这里的自我进化指交付流程的评估回流，不代表数字员工自动学习，也不代表模型自动取得规则审批权。

## 角色边界

- **产品体验设计师（你）**：制定和维护体验主张、主框架、交互模式、评价尺度；用试点发现规则缺口。
- **产品经理（主要使用者）**：定义业务目标、成功标准、业务例外、权限与发布范围；组织规格和验收，决定产品取舍。
- **校招生（实现与验证参与者）**：按规格补齐页面及状态，复用框架和组件，执行用例，报告冲突；不会的规则显式提问或登记，不能自行扩大范围。
- **研发与测试**：确认真实数据、权限、并发、接口和运行边界；验证服务端行为与上线条件。
- **AI**：起草、检查、生成和提出修正；不能把假设改写成业务事实，不能凭自评分放行。

## 如何证明“校招生也能交付”

用真实新需求做第二轮迁移：保持规范固定，让另一名校招生实现另一功能。记录导师提示、关键用例通过率和返工，不以第一份照抄示例的完成情况代替可复用性证明。详见试点计划。
