组内同学在本项目直接描述需求，助手按项目 Skill 执行。新增 [操作手册](09-execution-guide.md) 包含开工、实现、验收和失败恢复入口。目录现有 5 个配方，覆盖在线客服培训与 Skill 确认写入；未知需求会记录缺口并补配方，不保证任意需求自动合格。

## 先用起来

在支持本仓库指令的 AI 编程助手中打开项目，直接输入需求，例如：

> 我希望修改员工培训要求后先保存为候选存档，当前接待继续使用原版本。保存失败不能丢失输入，允许重试。

项目根目录的 `AGENTS.md` 与 `.agents/skills/jxl-design-io/SKILL.md` 提供执行入口；Cursor 对应入口在 `.cursor/rules/jxl-design-io.mdc`。这是由助手执行的工作流，不是网页内置的模型服务。

AI 负责提取意图、读取分层知识、补齐 Spec、绑定模板/组件/Token、实现和验证。组内同学无需手填 JSON 或选择组件；只有缺失信息会改变业务后果时才需要补充。未知业务不能自动套用培训模板。

每次输出保存在 `runs/<task-id>/`，包含需求、Spec、计划、代码绑定与证据。小单元逐项实现后仍需验证组合任务。

首个可运行样例：[需求](runs/save-candidate/brief.md)、[交互 Spec](runs/save-candidate/spec.md)、[验证报告](runs/save-candidate/verification.md)。重开预览：

```bash
npm run design-io:verify
npm run design-io:preview
# 打开 http://127.0.0.1:5274/design-io.html
```

以上命令验证内置保存样例；新功能必须加入自身绑定及用例，不能沿用样例通过结论。

## 三层范式，三类产出

| 参考范式 | 在京小灵里的作用 | 具体资产 |
|---|---|---|
| 设计工程 | 将六项主张、业务边界、框架与验收规则带入生成过程 | 主张、框架、Spec、组件引用、执行流程 |
| 动态交互 | 按用户意图和任务状态呈现必要信息与操作 | 意图路由、模板槽位、状态表、人工决策点、失败恢复 |
| 自我进化 | 用证据找出问题，修正规则后在另一功能中复验 | 验收报告、反例、规则变更记录、回归用例 |

这里的动态交互，可以先用确定的状态与共享组件实现，不要求首期上线由模型自由生成界面。这里的自我进化指交付流程的评估回流，不代表数字员工自动学习，也不代表模型自动取得规则审批权。

## 我们如何一起推进

我侧重体验框架、设计规则和关键方案；大家一起补齐业务知识，通过 AI 将共同标准落实到具体需求中。

- **需求与业务**：负责需求的同学明确目标、约束和成功标准，核对交付结果。
- **体验与规则**：我维护共享设计标准，参与关键方案讨论，并结合批次抽查完善规则。
- **实现与验证**：组内同学、校招生与 AI 按 Spec 复用组件、完成自检、整理证据。
- **真实落地**：与研发、测试一起核实接口、权限、并发及上线条件。

已有模式沿用共识推进，新模式和规则冲突带着具体方案一起讨论。详见 [组内协作方式](00-ai-design-paradigm.md)。

## 如何证明“校招生也能交付”

用真实新需求做第二轮迁移：保持规范固定，让另一名校招生实现另一功能。记录协作耗时、重复沟通、组内需求一次验收通过率、关键用例通过率和返工，不以第一份照抄示例的完成情况代替可复用性证明。详见试点计划。
