## 3. 建议两周试点安排

周期为规划建议，不是已承诺排期。

- 第 1–2 天：产品经理补业务输入，设计师确认主张/框架映射，研发确认应用范围与存档隔离可行性。产出冻结的 Spec 0.2。
- 第 3–5 天：校招生按 W02–05 做有固定数据的原型；每天只处理规则冲突和阻断问题。
- 第 6–7 天：按 16 条用例实际验收，组织用户任务观察；修复 P1，保存前后证据。
- 第 8–10 天：在第二功能上复用；真实联调视接口条件并行，不为赶周期把模拟改称真实。

建议至少两名校招生、两个边界相近的功能；只有一名时顺序执行，并注明学习效应。可选招募 5 名目标业务用户做形成性观察，只用于发现问题，不据此声称统计显著提升。

## 4. 需要测量的结果

| 指标 | 口径 | 建议目标与限制 |
|---|---|---|
| 规则可追溯率 | 有至少一条验收用例的关键 R-ID / 全部关键 R-ID | 100%；是规格质量，不是产品有效性 |
| 原型关键用例通过率 | 通过的适用关键用例 / 全部适用关键用例 | 交付时 100%，未执行计未通过 |
| 首轮通过率 | 首次独立验收通过的适用用例 / 全部适用用例 | 先测基线，再设提升目标 |
| 协作耗时 | 记录需求到验收的耗时及讨论、验证和规则维护投入 | 区分任务复杂度，避免只转移工作却误报节省 |
| 重复沟通 | 同一已有规则被重复解释或确认的次数 | 新模式讨论与业务变更单列，保留必要讨论 |
| 组内需求一次验收通过率 | 首次正式验收通过全部适用检查的需求数 / 进入首次正式验收的需求总数 | 缺证据不计通过；抽查发现首次遗漏回记；常规需求与新模式分组，报告样本数 |
| 返工轮次 | 首次提审后到 G1 通过的完整修正轮数 | 区分 Spec 缺陷、实现问题和业务变更 |
| 用户任务完成 | 无提示完成指定目标人数 / 参与人数 | 报人数和分母；有提示完成单独记录 |
| 状态理解 | 能正确指出当前生效版本、测试目标和下一步的人数 / 参与人数 | 追问事实理解，不只问“感觉是否可控” |
| 能力质量 | 固定业务集通过项 / 总项，附逐项依据、样本/模型/规则版本 | 原型模拟不计入真实能力数据；多次运行和业务抽检后再评价 |

业务任务脚本：让参与者更新一条培训要求，验证后应用；中途插入一个未通过样例和一次应用结果未知。观察其能否说清当前服务是否改变、哪项未通过、下一步如何恢复。不要提前教“正确答案”。
