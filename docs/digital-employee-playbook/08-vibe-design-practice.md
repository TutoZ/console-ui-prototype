# 京小灵 Vibe Design｜让设计经验成为组内可复用的交付能力

2026-09-16 · 组内实践方案 · [工作包入口](README.md)

**我们的目标是：组内同学只输入需求，AI 就能自动、稳定地使用正确的模板和组件，产出符合数字员工体验主张、产品主框架的 UI 和交互；校招生也能按同一套标准完成交付。**

“自动、稳定”是需要验证的建设目标。当前已有 AI Coding 案例、分层知识和局部验证样例，还没有证据证明任意需求都能一次合格。

## 1. 我们要沉淀的是设计判断

过去，组内提供 PRD，我分析体验问题，确定信息架构、布局、操作顺序、状态反馈和视觉表达，再通过与 AI 多轮调优把方案实现。决定最终体验的，不只是需求文档，还包括调优过程中不断补充的判断。

例如：为什么创建首屏先让用户描述目标；为什么 AI 修改前要让用户核对；为什么旧确认卡要失效；为什么认证中断后应该回到进度页；为什么员工搭建需要同时看到对话、配置和试用。

新范式把这些判断提前沉淀为有适用条件的规则，让下一次需求能够复用。我的工作重点随之增加一层：除了完成当前方案，还维护组内共同使用的体验标准、模板与评估方法。

## 2. 从已有案例中提炼什么

| 案例 | 设计问题与策略来源 | 应提炼的经验 |
|---|---|---|
| [Skill 创建与调优](cases/02-aop-skill.md) | Skill PRD + 我的《Skill 创建与调优体验重构》策略 + 调优对话 | 唯一起点、渐进呈现、确认回填、局部对比、过程反馈和业务语言 |
| [登录、认证与邀请](cases/03-account-onboarding.md) | 账号体系 PRD + 我在本任务提供的登录链路设计策略 | 入口层级、跨页上下文、等待与恢复、表单精简、权限解释和品牌连续性 |
| [自主搭建数字员工](cases/01-autonomous-employee.md) | 员工 PRD + 调优对话 + 当前交互 | 对话、配置和试用协同；复用交互同时保持员工内容语义 |

案例统一按“需求场景 → 体验问题 → 设计策略 → 调优证据 → 当前界面 → 可复用规则 → 体验验证”组织。历史画面缺失时，使用明确标注的策略描述，不补造前后对比。源码存在某个分支与用户实际操作通过分别记录。

三个案例也说明规则需要条件：Skill 创建强调先描述、再展开；员工搭建曾明确要求三个区域同屏。不能把其中一个布局提升为全产品默认。

## 3. 六层知识如何服务视觉和交互

| 文件 | 存什么设计知识 | 从案例提炼的例子 |
|---|---|---|
| product.md | 用户任务、体验主张、产品主线和框架位置 | Skill 创建不能跑成员工创建；邀请登录要延续加入企业的任务 |
| domain.md | 会影响界面、状态和操作后果的业务条件 | “申请已提交”与“已经加入”不同；审核中再次进入应显示哪个状态 |
| templates.md | 适用场景、信息结构、必需槽位、展开时机与排除条件 | Skill 对话与编辑工作区；邀请上下文、申请表单、结果区 |
| components.md | 真实组件入口、变体、属性、事件与状态支持 | 确认卡怎样只读；分栏怎样调整；字段和反馈怎样复用 |
| design.md | 品牌、字体、色彩、间距、层级和视觉 Token | 主动作与辅助动作的层级，状态文字与颜色，统一表单样式 |
| craft.md | 等待、焦点、滚动、长内容、错误、恢复和动效 | 写入不抢操作位置；旧卡仍可读；失败保留输入 |

domain 在这里为设计提供必要边界，不展开后端架构建设。设计也不能凭界面决定未确认的业务，例如用一个“成功”状态替代申请、审批和加入三个阶段。

## 4. 规则必须让 AI 知道什么时候用、怎样做、怎样验

每条规则至少包含以下内容，AI 从自然语言需求中选择，不要求组内同学手工填写。

| 项目 | 示例：Skill 确认写入 |
|---|---|
| 来源与状态 | 设计策略及 S05 调优证据；候选规则，迁移验证前不称稳定规则 |
| 适用条件 | AI 将修改当前 Skill 内容 |
| 不适用条件 | 纯问答、解释写法、用户自己编辑；不强制每句话都确认 |
| 体验目的 | 修改可预期，用户知道什么将变化 |
| 结构元素 | 本轮变更摘要、目标区域、确认动作、轮次状态 |
| 组件映射 | SkillRoundConfirmCard；与编辑区域的写入事件关联 |
| 视觉约束 | 沿用组件现有样式与已核实 Token；有效、已确认、已失效可区分 |
| 交互要求 | 确认后写入；新方案出现后旧方案只读；不强制切换当前工作位置 |
| 验收断言 | 未确认不覆盖；旧卡不提交；写入对象对应；状态不只靠颜色表达 |

“主按钮色”“禁用态”等是视觉角色，不是已经存在的 Token 名称。执行时必须查询 design.md 和源码，填写真实导出或变量及其作用位置；没有对应就记录缺口，不自行发明品牌值。

## 5. 组内实际怎样使用

**第一步，提供需求。** 大家在项目的 AI 助手里输入业务目标、已有要求和预期结果，也可以直接提供 PRD。例如：

> 优化被邀请人加入企业的流程。登录前后都能看清加入哪家企业；申请成功后明确等待审批；邀请失效时说明下一步。请沿用京小灵现有组件和视觉规范，输出可交互方案并做体验验证。

**第二步，AI 输出简短设计理解与 Spec。** 明确用户当前任务、主要体验主张、页面结构、状态与操作关系。已有规则直接采用；会改变体验方向的缺口单列。不要让大家先学模板编号或选组件。

**第三步，AI 按小单元实现。** 先做邀请上下文提示，再做申请反馈，再做失效状态；各自核对后连接完整路径。不能因为每个单元通过，就跳过登录前后的上下文连续性检查。

**第四步，AI 自检并交付。** 给出可打开页面、关键状态画面、Spec 对照、问题和修正记录。组内同学围绕任务是否完成评审；我关注关键体验、视觉一致性和新模式，常规模式通过抽查与复盘维护。

**第五步，问题回流。** 如果重复解释“旧卡不能再提交”，把触发条件和验证项补入规则；如果出现新模式，就记录新适用条件。避免只改这一次页面，下一次仍重新解释。

当前这些步骤由支持仓库指令的 AI 助手执行，预览网页本身不是自然语言生成平台。案例新增的规则仍需登记、绑定和复验，文档更新不等于自动接通全部组件。

## 6. 一份交互 Spec 应具体到什么程度

以“邀请申请已提交”为例，以下是候选规格，不代表已完成运行验证：

| 项目 | 规格 |
|---|---|
| 用户目标 | 知道申请是否提交，以及接下来做什么 |
| 上下文 | 保留目标企业名称，区分登录身份与申请对象 |
| 页面层级 | 结果标题 → 当前状态 → 下一步说明 → 必要操作；不重复展示完整可编辑表单 |
| 文案语义 | 显示“申请已提交，等待管理员审批”，不写“已加入企业” |
| 视觉 | 复用结果布局与状态样式；标题、说明、操作层级清楚；长企业名不遮挡操作 |
| 交互 | 提交期间防重复，失败保留输入；成功后不继续显示可重复提交入口 |
| 恢复 | 再次进入按已确认规则恢复申请状态；未知规则标记待补充 |
| 验证 | 分别检查企业对应、状态文案、重复触发、错误保留、长内容和键盘操作 |

规格需要同时约束内容、画面和行为。只写“简洁、美观、符合规范”不足以让 AI 稳定执行。

## 7. Design Evaluator 怎样判断体验合格

| 维度 | 核对重点 | 证据 |
|---|---|---|
| 主线与信息架构 | 是否围绕当前任务；主动作清楚；专业能力是否按阶段呈现 | Spec 与完整路径对照、任务观察 |
| 视觉遵从 | 真实组件及 Token 是否正确；字体、间距、对齐、状态层级是否一致 | 代码绑定与实际渲染画面对照 |
| 交互遵从 | 确认、写入、取消、恢复、等待与错误是否按规定工作 | 原子操作记录与完整流程试跑 |
| 体验理解 | 用户能否判断当前状态、操作后果和下一步 | 组内走查与用户任务反馈，注明样本 |

建议每次固定记录常用宽度、窄宽、长文本，以及默认、等待、成功、失败、禁用等适用状态。具体宽度沿用项目约定；需要新增基准时明确登记。视觉比较必须使用同状态、同内容尺度的基准，不能拿成功态截图证明异常态合格。

关键主线或操作失败时，整体不判合格；其他检查仍分别保留结果。没有操作证据写“未执行”，不以源码存在代替体验通过。自动检查负责发现可规则化问题，视觉层级和任务理解仍需实际观察。

## 8. 如何验证这套范式是否有效

先从已有案例提炼规则，固定版本，再让另一位组内同学或校招生输入一条未参与规则提炼的新需求。保留 AI 初次产出、补充调优、最终结果和评估证据；采用相近任务与一致标准比较。

重点记录：适用视觉／交互断言通过率、首次体验验收通过率、需要设计师重复解释的已有规则数、返工轮次，以及包含规则维护在内的协作时间。未经执行的适用断言不计通过；新模式探索与重复纠错分开。

Skill 策略中的创建时长、手动字段数、初稿采纳率，以及登录策略中的开通转化率、路径长度与用户反馈，属于产品体验效果指标。它们用于验证具体方案；不能直接代替“AI 是否更遵从设计规则”的验证。当前没有实测值，不声明效率或转化已经提升。

我们最终交付的是可运行界面、可追溯 Spec、真实组件与 Token 绑定、体验验证记录，以及经过复验的规则。这样，已有设计经验才能在下一次需求里继续发挥作用。
