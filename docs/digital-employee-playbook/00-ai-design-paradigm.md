# 京小灵 AI 新范式：从产品意图到可验证的体验交付

**以体验主张定义方向，以分层知识约束生成，以真实组件承载结果，以验证推动改进。**

版本：1.0 · 2026-09-08  
文档定位：团队共识与落地方案  
适用范围：我们组的需求设计与交付。大家共同沉淀业务和体验共识，由组内一名体验设计师侧重维护设计体系，并与研发、测试一起推进落地。

## 一、我们要建立什么

**核心目标：把我们已有的产品理解和设计经验沉淀成 AI 可执行的规则，让组内同学从需求出发，更高效地完成符合规范的功能设计与验证，把更多精力放在关键体验和产品创新上。**

我们用自然语言描述业务需求，AI 自动理解需求、读取适用规范、生成交互规格、复用项目组件完成界面，并提交可核验的结果。组内同学无需先学习模板编号、组件接口和 Token，也无需手工编写结构化计划。

例如输入：

> 我希望修改员工培训要求后先保存为候选存档，当前接待继续使用原版本。保存失败不能丢失输入，允许重试。

系统应产出围绕这一目标的交互与实现：明确当前员工和在岗版本、提供培训输入与保存入口、展示候选存档、处理等待和失败，并验证保存不会改变在岗版本。每个元素都能追溯到需求或规范。

“自动、稳定、符合规范”是建设目标。稳定性需要通过不同需求、不同执行者的重复交付来证明。当前已完成一个隔离样例，尚不能承诺任意业务都能自动合格。

## 二、为什么需要新的设计交付方式

数字员工平台的核心用户是管理者：用户关注把什么工作交给谁、执行到哪里、何时需要介入、结果是否达标。自主执行和不确定产出，要求界面同时解释能力边界、工作状态和控制后果。

对应的设计交付也需要覆盖这些行为。仅交付一张成功态画面，无法说明保存是否生效、超时是否成功、重试是否重复执行、哪些会话受到影响。仅提供组件库，也无法决定哪个组件适用于当前业务。

因此，设计资产需要同时包含目标、业务含义、结构、视觉、交互和验收依据。AI 在这些约束下完成具体需求，设计师通过每次交付中发现的问题完善资产。

| 交付要素 | 本范式的要求 | 作用 |
|---|---|---|
| 设计主张 | 转为可观察的行为标准 | 确定什么是好的数字员工体验 |
| 产品与业务知识 | 区分全局主线与具体业务规则 | 保持需求范围和动作含义准确 |
| 模板与组件 | 建立结构、真实接口、Token 的对应关系 | 让生成落到现有产品体系 |
| 交互 Spec | 明确状态、触发、反馈、恢复和后果 | 让实现者与评审者依据一致 |
| 质量评估 | 分开检查代码、交互、视觉和业务 | 让结论有相应证据 |
| 规则回流 | 将问题修正到所属知识层 | 让后续需求复用已验证经验 |

## 三、好的数字员工体验：六项主张如何落地

六项主张保留用户原定义，并通过具体行为用于设计和验收。

| 主张 | 用户应感受到什么 | 功能设计要求 | 可观察的验收问题 |
|---|---|---|---|
| 轻松上手感 | 学得轻松、用得顺手、看得统一 | 沿用框架与术语；主动作清楚；反馈及时 | 用户能否找到下一步？跨页操作是否一致？ |
| 完全掌控感 | 它在做什么，我看得见、管得住 | 状态与生效范围可见；在业务允许的位置提供介入、取消或接管 | 用户能否判断操作后果？介入是否在约定范围内生效？ |
| 踏实干活感 | 看得见它出力，成果用数据说话 | 过程可回溯；结果有来源、口径和版本 | 数据能否追到任务？是否区分模拟与真实执行？ |
| 真实拟人感 | 像管理一个员工一样协作 | 岗位、职场语言和协作方式一致；动作语义准确 | “培训、上岗、交接”等词是否准确表达实际行为？ |
| 养成归属感 | 我能培训它，改进有反馈 | 修改、存档、测试、应用和反馈关联 | 用户能否看清教了什么、是否有效、何时应用？ |
| 专业胜任感 | 清楚它是谁、擅长什么、能干什么 | 岗位能力与边界明确；有适用条件和证据 | 是否避免夸大能力？能否据此选择合适员工？ |

建议以轻松上手作为基线，以掌控、过程透明和能力可预期建立信任，再通过协作和培养形成长期关系。每个功能选择主要主张，同时守住其他适用基线，不要求每个页面展示全部六项。

拟人表达有助于建立协作心智；可靠性仍需能力证据和真实结果支持。“会成长”也需要实际学习、记忆或配置变更机制，不能仅用等级动画证明。

## 四、知识分层：让 AI 在正确边界内工作

知识按责任划分为六份入口文档，覆盖五种层级。Spec 是本次需求的执行契约；Evaluator 是独立的质量评估环节。

| 层级 | 文件 | 回答的问题 | 维护重点 |
|---|---|---|---|
| 产品级 | product.md | 为谁服务？主线是什么？遵守哪些主张和框架？ | 用户角色、范围、全局对象、跨页连续性 |
| 业务级 | domain.md | 这个动作是什么意思？需要什么资格？何时生效？ | 状态、权限、前提、异常、指标口径 |
| 仓库级 | templates.md | 当前任务适合什么结构？必须有哪些元素？ | 意图匹配、槽位、适用条件、排除条件 |
| 仓库级 | components.md | 哪个真实组件承载元素？接口和能力是什么？ | 导入路径、属性、事件、状态与缺口 |
| 品牌级 | design.md | 元素应如何呈现？使用什么视觉角色和 Token？ | 色彩、字体、层级、样式来源及冲突 |
| 通用级 | craft.md | 操作是否顺手、可恢复、键盘可用？ | 焦点、等待、错误、空态、窄宽和长内容 |

product.md 和 domain.md 优先决定需求主线。例如“保存培训”在在线客服域中被定义为生成候选存档，不能由组件默认行为推导为立即应用。质检也有培训入口，但必须加载质检规则，不能因为同一个词就继承客服的资格和状态。

每条重要规则应携带适用范围、来源、版本、维护者和状态。现状观察、建议、已确认规则需要明确区分；源码描述当前实现，已确认的新需求决定改造方向。存在冲突时记录差异与责任层，不将猜测写成事实。

按阶段只读取必要知识：规划加载产品和当前业务域；结构设计加载选中模板；组件设计加载对应接口和 Token；交互验证加载适用工艺和用例。这样减少无关规则混入，也便于定位错误。

## 五、主框架：每个新功能接入同一套产品结构

京小灵功能按“平台与团队 → 数字员工 → 业务域 → 员工工作区 → 任务与结果”组织。新增功能首先确定所属位置，保留团队、员工和业务对象关联，复用现有导航与上下文。

重点保持三条链路连续：

1. 员工生命周期：选择、雇佣、培训、测试、上岗、工作、复盘。
2. 工作任务：表达目标、补充信息、确认范围、执行、介入、交付、验收。
3. 能力演进：反馈、修改草稿、保存候选、测试、确认应用、跟踪效果。

各业务可以裁剪流程，但需说明如何保持控制和验收要求。员工在岗状态、任务状态、候选配置状态和测试资格分别表达。例如“V1 在岗”和“V2 尚未测试”可以同时存在。

新功能必须回答：放在哪里、操作谁、改变什么、何时生效、失败怎么恢复、结果如何追溯。具体约束见 [主框架契约](02-framework-contract.md)。

## 六、从一句需求到交付的执行流程

| 阶段 | AI 的工作 | 交付物与检查点 |
|---|---|---|
| 1. 理解意图 | 提取业务域、对象、动作、结果、约束和不做事项；识别缺失信息 | 需求摘要；关键业务假设显式标注 |
| 2. 形成 Spec | 选择主张和业务规则；明确状态、反馈、异常及验收 | 单功能交互规格；每条要求可验证 |
| 3. 选择结构 | 按业务域、对象、动作、结果匹配模板；拆分多动作任务 | 模板与槽位计划；无匹配不得默认套用 |
| 4. 绑定实现 | 检查真实组件接口，映射视觉角色与 Token | 代码与绑定清单；新增元素有依据 |
| 5. 分单元验证 | 先检查状态转换，再实际操作和查看画面 | 代码测试、交互观察、视觉问题与修复记录 |
| 6. 验证完整任务 | 检查上下文交接、前后步骤、真实业务依赖 | 组合验证与未完成项 |
| 7. 交付与回流 | 输出可打开结果和证据，将问题回写所属层 | 交付报告、规则修订与后续复验项 |

自然语言理解由 AI 完成，结构化路由器核对规范化后的字段。大家不需要手填 JSON。只有缺失信息会改变业务后果时才需要补充，例如“停止任务”是否中断正在执行的会话；布局和已知组件选择由 AI 按规范处理。

没有模板时，先核实业务规则与可复用组件，定义新配方及正反例。没有业务依据时，可生成明确标注假设的隔离原型，但不能声称真实能力已具备。

## 七、让意图与模板元素真正接通

映射链路为：

**用户意图 → 业务规则 → 模板槽位 → 真实组件/样式导出 → Token 角色 → 验收断言 → 证据。**

以“保存候选，不影响当前接待”为例：

| 意图需要 | 模板元素 | 项目实际承载 | 验证重点 |
|---|---|---|---|
| 明确当前员工 | context | OnboardingWorkspaceHeader，组合员工和版本信息 | 保存前后仍是同一对象 |
| 编辑与状态同屏 | layout | ResizableSplitPane，容器使用 PANEL | 两栏可读，操作不丢失 |
| 输入培训要求 | fields | 原生多行字段，FIELD / LABEL | 输入有标签，失败后保留 |
| 保存候选 | save | 原生按钮，BTN_INK | 只保存；重复触发受保护 |
| 区分候选与在岗 | candidate_status | badgeClass 和状态文字 | V2 尚未应用，V1 仍在岗 |
| 表达等待 | busy | ContentBusy | 请求状态可见，不抢焦点 |

K-* 编号是工作包中的语义映射标识，不能当作源码已经存在的 CSS 变量。绑定还需要区分组件内部样式、外部容器样式和元素样式；仅有同名组件或路径，不足以证明正确复用。

目前项目样例通过 AST 校验真实导入和槽位引用，并通过浏览器观察最终布局。静态检查无法证明所有运行分支与视觉细节正确，两类证据需结合使用。

## 八、交互 Spec：把主张写成可执行要求

每份 Spec 至少包含目标、对象与入口、采用规则、状态表、组件和 Token 绑定、异常恢复、最小断言、组合流程、数据模式与未决项。

以下为保存单元的规格片段：

| 项目 | 要求 |
|---|---|
| 用户目标 | 保存新培训要求，当前接待保持原版本 |
| 主要主张 | 完全掌控感、养成归属感 |
| 前置状态 | 当前 V1 在岗，有非空且已修改的草稿 |
| 触发 | 用户选择保存培训 |
| 等待 | 展示正在保存，阻止重复请求，保持可理解的焦点位置 |
| 成功 | 显示候选 V2 尚未应用，当前在岗版本仍为 V1 |
| 失败 | 保留输入，说明失败，允许重试 |
| 明确不做 | 不自动测试、不应用、不新增导航 |
| 数据边界 | 演示数据仅证明交互；生产依赖服务端回执、权限和版本隔离 |

测试按最小单元拆解。例如“保存后在岗版本不变”“保存后候选生成”“失败后输入保留”分别验证。每个单元聚焦一个首要断言，能直接定位失败原因。

小单元通过后，仍要执行保存→测试→应用的组合流程，检查版本关联、状态交接和返回恢复。缩小单次生成与测试范围，不缩小完整任务的验收范围。

## 九、Design Evaluator：有证据地判断质量

评估分四层进行，任何一层都不能由另一层的通过结论替代。

| 层级 | 检查内容 | 适用证据 |
|---|---|---|
| L0 知识与映射 | 主线、业务域、规则来源、模板槽位、组件和 Token | 计划检查、路径/导出检查、源码版本记录 |
| L1 交互单元 | 正常、失败、等待、重复触发、输入保留、焦点 | 状态测试、实际点击、DOM 观察及相应用例证据 |
| L2 组合任务 | 步骤衔接、对象连续、版本关联、生效范围 | 完整流程记录、接口和集成验证 |
| L3 任务与体验 | 用户能否理解并完成工作，视觉是否合适，业务是否达标 | 设计评审、用户任务观察、真实业务数据 |

报告应列明检查项、环境、观察、证据和未完成项。缺证据标记未执行，环境障碍标记阻塞；不得用综合分抵消主路径失败，也不能将模拟结果当作真实能力提升。

质量问题按责任层回流：任务跑偏修订 product；动作含义或资格错误修订 domain；结构缺失修订 templates；接口误用修订 components 或实现；视觉角色错误修订 design；焦点与恢复问题修订 craft 或实现。

本轮实际发现：保存按钮切换原生 disabled 后丢失键盘焦点。样例改用 aria-disabled 配合处理函数拦截，并复验焦点保持和重复回车不新增存档。经验已写入 craft.md，供适用场景复用。

## 十、我们如何一起推进

业务理解、体验标准和交付质量是我们共同沉淀的组内资产。我侧重体验框架、设计规则和关键方案，大家一起补齐业务知识，通过 AI 把这些共识落实到具体需求中。

| 协作环节 | 我们各自侧重什么 | 一起形成的结果 |
|---|---|---|
| 需求与业务 | 负责需求的同学说明目标、约束和业务取舍，相关同学一起补齐关键条件 | 清楚的需求范围与成功标准 |
| 体验与规则 | 我侧重主张、框架、交互模式和视觉标准，结合大家遇到的问题持续完善 | 我们共同使用、可执行的体验标准 |
| 实现与验证 | 需求同学、校招生和 AI 按 Spec 复用组件、补齐状态、执行检查 | 可运行的方案及可核验的证据 |
| 真实业务落地 | 与研发、测试一起核实接口、权限、并发和生效范围 | 原型与真实运行边界清楚的交付结果 |
| 经验沉淀 | 大家记录问题，AI 协助定位和整理，再由相应职责的同学确认规则变更 | 后续需求能够直接复用的规则和案例 |

### 不同需求，采用合适的协作方式

| 需求类型 | 我们怎么推进 | 体验设计的关注点 |
|---|---|---|
| 已有模式内的常规需求 | 负责需求的同学与 AI 沿用已有规则完成方案和自检，按批次一起复盘 | 抽查体验一致性，将共性问题补进规则 |
| 新交互模式、主导航或跨页框架变化、设计规则冲突 | 带着具体方案和问题一起讨论，确定方向后继续实现与验证 | 在关键方案点参与，形成可复用的新模式 |
| 权限、生效范围、业务承诺或真实接口变化 | 负责需求的同学与研发、测试确认业务后果，补齐相应验证 | 一起检查控制、状态表达和恢复体验 |

讨论时，AI 协助准备相关画面、适用规则、验证结果与推荐方案，让大家围绕具体问题快速达成共识。校招生也沿用同一套规则和案例推进，遇到缺口再一起补齐。

常规需求沿用已有共识即可推进，不必逐页重新确认；关键方案保留必要讨论。每个需求仍需完成适用验收，真实上线沿用团队现有流程。

我们可以直接这样描述需求，也可以用普通自然语言表达同样内容：

> 我希望【谁】在【什么场景】完成【目标】。必须满足【约束】，完成后应看到【结果】。请按京小灵规范实现并验证。

仓库中的 AGENTS.md、项目 Skill 与 Cursor 规则提供执行入口。它们需要由支持这些指令的 AI 助手执行；当前预览页面本身没有内置自然语言生成服务。

| 真实业务和完整链路 | 尚未完成真实接口联调与保存→测试→应用组合验收 |
| 全仓质量 | 存在其他文件的类型或缺失模块错误，不能宣称全仓检查通过 |
| 泛化稳定性 | 尚未完成另一需求、另一执行者的迁移验证 |

下一轮建议用“查看历史存档”验证同域新动作，再选择质检等独立业务域验证知识隔离。由另一位组内同学提出需求、另一名校招生参与交付，保留原始需求、规则版本、初次结果、修正和证据。

我们同时关注交付质量与协作效率：适用原子断言通过率、完整任务完成率、无来源元素数、跨域规则误用数，以及组内需求一次验收通过率、重复沟通次数、返工轮次和从需求到验收的耗时。

“组内需求一次验收通过率”指首次正式验收即通过全部适用检查的需求数 / 进入首次正式验收的需求总数；缺证据不计通过，后续抽查发现首次验收遗漏的问题应回记。“重复沟通”指对同一已有规则重复解释或确认；新模式讨论和业务变更单独记录。规则维护时间也纳入协作成本，避免只转移工作却误报效率提升。

对比时区分常规需求与新模式，记录复杂度、执行者和样本数。未执行用例计入适用断言分母；代码测试通过率单独记录。我们以相近质量要求下的重复交付结果判断改进，不能通过减少必要讨论或少测来制造效率提升。
