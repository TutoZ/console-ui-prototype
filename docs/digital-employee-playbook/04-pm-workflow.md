# 组内执行流程｜让规范进入每一次交付

我们沿用共同的业务与体验标准推进需求。我侧重框架、规则和关键方案，负责需求的同学与 AI 完成具体方案和验证；遇到新模式或规则冲突一起讨论，常规需求按批次复盘。

## 1. 从意图到证据的六步

| 步骤 | 输入 | 需求同学的判断 | 校招生与 AI 的工作 | 交付闸门 |
|---|---|---|---|---|
| 1 定义任务 | 需求、现有页面、用户问题 | 为谁做，成功是什么，本期边界 | 整理输入卡和事实/假设 | 有一个可验证的任务结果 |
| 2 形成 Spec | 主张、框架、规则 | 确认业务条件与生效范围 | 生成状态表、异常和验收用例 | 无关键规则冲突；框架沿用既有契约，变更时请设计师判断 |
| 3 结构与组件 | 通过规格评审的 Spec | 判断入口和主路径是否合理 | 复用页面外壳与组件，做结构稿 | 能指出各规则的界面承载位置 |
| 4 完成交互 | 状态/数据/文案表 | 确认模拟与真实边界 | 制作可运行原型，补齐异常和恢复 | 主路径及阻断用例可复现 |
| 5 收集证据 | 固定用例、原型/环境 | 对实际结果作判断 | 实际操作、保存证据、记录问题 | 按评估机制放行，缺证据不通过 |
| 6 修正复用 | 失败记录、对照样例 | 决定改需求、规则还是实现 | 修复并复验，更新规范和用例 | 在另一需求验证规则可复用 |

业务条件和框架一经确认，校招生在范围内自行完成可逆实现；不为每个组件、常规文案或排列顺序重复找负责人确认。改变生效范围、权限、主导航或业务承诺时，先提交具体影响和推荐方案。

## 2. 我们输入需求，AI 准备执行材料

负责需求的同学输入目标、约束和预期结果，有业务材料时一并提供；AI 从仓库检索实际页面与源码、product.md、domain.md 的选中业务域，整理意图卡、匹配模板及组件绑定、成功和失败样例。无需大家手填 JSON 或手选组件。按阶段加载，不一次附上全部业务知识。没有数据或接口时允许使用注明的模拟数据；必须保留将来验证真实行为的用例。

## 3. 可复制给 AI 的指令

以下是普通任务提示词，不是自动安装的技能。先提供相应文件内容或让工具读取文件，不能只报一个文件名就假设模型已读。

### A. 把需求变成 Spec

```text
你协助我为京小灵编写单功能交互 Spec。我正在推进组内需求，业务意图见下方自然语言需求。
先读取 product.md、domain.md 的共性及匹配业务域、03-spec-template.md 和实际功能源码。
需要解释主张/F规则时按引用读取。生成并冻结 domain/object/action/outcome，列出不做事项。
形成 Spec 后才按 templates.md 选择模板槽位，再加载所需 components.md 条目与 design.md Token绑定。
输出：现状事实与证据、拟改行为、1–3 项主要体验主张、入口与框架关系、完整 Spec。
每条关键行为给 R-ID，映射 E-ID/F-ID 和 Given-When-Then 验收用例。
明确草稿/运行、真实/模拟、自动动作/人工决策；覆盖失败、权限、重复操作和结果未知。
缺失信息列为假设并给推荐默认值。可以继续起草，但不得编造业务规则已获确认、接口已实现或测试已通过。
此阶段不修改产品代码。
需求：〔粘贴自然语言描述〕
```

### B. 按 Spec 制作功能

```text
按附带的已评审 Spec 实现京小灵功能。先核对意图冻结卡及槽位/组件/Token映射。
每次完成一个原子单元，携带相关规则与固定数据；原子单元通过后保留组合流程验证。
使用 design-evaluator.md 检查映射与证据，不能把静态通过当成功能通过。
说明你将复用哪些结构，列出本次改动与每条 R-ID 的对应；随后完成范围内实现。
保留现有团队/员工上下文、视觉规范和词表；不另造全局外壳。
为正常、失败、权限、超时与冲突状态提供可重复的测试数据和复位方式。
模拟接口必须明确标注，不用随机成功代替验收，不调用真实对外发布动作来演示。
遇到规则冲突，列出事实、影响与推荐方案，不擅自改变业务边界。
交付可运行入口、运行步骤、变更摘要、用例结果和待联调项。
```

### C. 按证据验收

```text
按 design-evaluator.md、06-evaluation.md 与原子/组合验收用例检查当前版本。
先检查产品主线、业务域隔离、槽位与Token映射；再实际操作取证。
先记录环境、功能版本、测试数据、角色、真实/模拟范围。
逐项操作并收集证据；检查可见反馈和实际状态/副作用，不以代码存在代替功能通过。
输出每条用例的通过/失败/阻塞/未执行、证据位置、问题及受影响的 R-ID/E-ID/F-ID。
遇到结果未知不得标成功；未实际操作的项目不得标通过。
先列阻断项，再给体验质量判断，最后给可复现的修正建议。
不要替产品经理批准业务上线，也不要因自己的综合分较高忽略关键失败。
```

### D. 将问题回流为规则

```text
根据验收失败记录，判断问题源于需求、体验主张解释、框架、Spec、组件、实现还是评估方式。
给出最小修正、影响范围、对应反例和回归用例。
规则确需改变时写出旧规则、新规则、为什么改变；保留原来的失败记录。
在另一个输入或另一功能上验证修正，避免只为当前演示写特殊分支。
```

## 4. 例会只讨论三类事项

- 业务取舍：哪些结果和边界是本期承诺，依据是什么。
- 规则冲突：具体冲突位置、影响与可选择方案。
- 证据差距：哪条用例失败或缺证据，由谁补齐。

不以“感觉更智能”“再像员工一点”结束评审。把意见写成“在什么条件下，哪个用户看见什么、能做什么、如何确认结果”。
