# 京小灵需求到交互实现

从仓库根目录解析以下路径。用户只需描述需求，Agent 负责其余材料与执行；不要将这个工作流解释成独立网页内置的模型服务。

## 需求与规则

先读 `docs/digital-employee-playbook/product.md` 与 `domain.md` 的相关业务域，检查实际页面与源码。提取业务域、对象、动作、预期结果与不做事项。一个多动作需求拆成可验证单元，保留完整用户任务。

不要用关键词路由替代需求理解。缺失会改变业务后果的信息时，给出可供用户回答的具体问题；继续不依赖该信息的可逆工作。常规布局和组件选择自行决定。没有确认的业务规则可作为明确标注的原型假设，不用于真实发布。

## 结构与实现

读取 `templates.md` 的匹配结构、`components.md` 的对应条目和 `design.md` 的Token绑定；项目 `.cursor/skills/design-system-index` 的相关规范补充样式细节，实际导出和共享源码决定可调用接口。

- 目录现覆盖在线客服培训与 Skill 确认写入。目录无匹配时，查真实组件与业务规则，为本需求定义新配方及正反例；知识不足时登记缺口。不得把“无匹配”改成默认在线客服。
- 为本次需求在 `docs/digital-employee-playbook/runs/<task-id>/` 保留 brief.md、spec.md、plan.json、代码绑定清单与证据报告。无需为轻微文本修改建立整套重型产物。
- 实现真实代码，导入现有共享组件及样式，不交付“看起来像组件”的手抄 HTML。优先在现有业务位置落地；独立试跑可使用 `design-io.html`，不得擅自替换其已存在的其他试跑。
- 不随意新增主导航，不改无关业务。候选配置与线上状态分开，外部影响范围依用户授权。
- 组件内部Token、外部容器样式、语义建议三种绑定分开记录；函数/路径存在不代表已经应用样式。

## 验证与回流

先写原子断言，按小单元实现，再做组合任务。参照 `craft.md` 与 `design-evaluator.md`。

1. 运行 `npm run design-io:plan -- --plan <plan.json>` 校验声明（模板未登记前先补齐业务契约与目录）。
2. `npm run design-io:verify` 验证内置样例的真实导入/构建/状态行为；新功能需为自身增加 bindings 和测试，样例通过不能当新功能通过。
3. 通过现有 dev server 打开真实入口，检查正常、失败/恢复和至少两种宽度；可用浏览器工具时实际点击和截图。无法操作时记录阻塞，不写“验收通过”。
4. 输出运行态、视觉、业务三类证据与限制。综合分不能抵消主路径失败。普通可逆修复继续执行，关键规则冲突回到所属层，不反复无范围生成。

完成时交付用户可打开的结果与简短验证摘要，组内同学不需要学习内部文件结构。不要宣称“任意需求保证全自动合格”；未知业务的质量来自补齐规则、复验与扩大覆盖，而不是跳过检查。

## 工作包 0.3 的逐任务执行入口

机器目录现有五个配方：在线客服培训四个，Skill 确认写入一个。以 catalog.json 为覆盖依据，案例文档不等于机器配方。

助手理解自然语言后生成 intent.json（字段见 examples/skill-confirm-intent.json），再执行 `npm run design-io:start -- --intent <intent.json>`。组内同学无需手填。start 精确匹配并生成 runs/<task-id> 的 plan、Spec 草案和全为 not_run 的结果清单；同名任务拒绝覆盖，已有任务直接继续。命令不调用模型，不能替代需求理解。

补齐生成的 Spec：真实入口、目标对象、采用主张、布局与状态、组件属性、Token 作用位置、异常恢复及完整任务。完成代码后为本任务生成 bindings.json，执行 `npm run design-io:bindings -- <bindings.json>`，同时做适用类型/行为检查。保留默认样例；新试跑通过独立入口接入。

原子结果填入本任务 results.json，证据文件放本任务目录；随后执行 `npm run design-io:review -- --run <run目录>`。缺少操作/截图、not_run、failed 都不会获得 ready_for_human_review；此状态也仅表示证据清单齐全，不能宣称视觉已自动验收。实际打开页面核对至少两种宽度与关键状态，在 visual-review.md 记录观察。工具不可用时交付实际限制，不能用模板文字填充“已通过”。

来源漂移时先看差异，不自动更新哈希；已复核变化记录来源版本，品牌冲突保留。未知意图输出无匹配并继续做本需求必要的规格、真实组件和新配方；不要让用户挑模板，也不要填虚构 employeeId 通过校验。轻微文案改动仍可轻量交付。
